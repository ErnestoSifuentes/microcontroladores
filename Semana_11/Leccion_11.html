1. El tiempo se genera con un temporizador, no con un retardo

Un cronómetro digital requiere una referencia temporal conocida. Si el contador principal se incrementa dentro de un bucle con retardos, la duración de cada iteración cambia cuando se actualiza la pantalla o se procesa un botón. La arquitectura más robusta utiliza Timer_A para crear una base de tiempo regular y una variable de tiempo transcurrido. La visualización puede actualizarse con menor frecuencia que la base de tiempo, sin afectar la cuenta.

Si el temporizador produce un tick cada 10 ms, cien ticks equivalen a un segundo nominal. Es necesario distinguir frecuencia configurada de frecuencia real: el error del reloj se acumula durante mediciones prolongadas. Un contador de milisegundos debe contemplar su posible desbordamiento y el acceso concurrente desde la ISR.

2. Máquina de estados y botones Start/Stop, Reset y Lap

La guía del Proyecto 2 propone un cronómetro con pantalla OLED y controles de inicio/detención, reinicio y vuelta (lap). La lógica se expresa mejor como una máquina de estados: READY espera una orden, RUN acumula ticks, STOP conserva el último tiempo y LAP registra una marca sin necesariamente detener el reloj. Una transición debe indicar tanto la condición de entrada como la acción sobre las variables.

Los pulsadores necesitan filtrado porque un solo rebote puede provocar Start seguido de Stop. Conviene mantener separadas la captura de eventos, la modificación del estado y el refresco gráfico. El simulador permite probar la lógica antes de compilar el proyecto en CCS.

3. OLED SSD1306 e interfaz I²C

Una pantalla SSD1306 puede emplear el bus I²C, que utiliza dos líneas con funciones distintas: SCL transporta el reloj y SDA transporta los datos. En el MSP430G2553 la interfaz USCI_B0 utiliza funciones multiplexadas de P1.6 y P1.7. Ambas líneas requieren resistencias de pull-up adecuadas a la alimentación y la capacidad del bus; algunas tarjetas OLED las incorporan. Las direcciones I²C y bibliotecas dependen del módulo real.

Las tramas de actualización de pantalla consumen tiempo. El programa debe enviar sólo las regiones necesarias y evitar operaciones bloqueantes prolongadas en una ISR. La RAM limitada del MSP430G2553 obliga a revisar el almacenamiento de un framebuffer completo y, si fuera necesario, usar transferencias por páginas o buffers pequeños.

4. Práctica 5: PWM para controlar un motor

La práctica complementaria solicita control de velocidad mediante PWM. El pin no alimenta directamente el motor: se utiliza un transistor o módulo de potencia, con protección apropiada ante cargas inductivas. El porcentaje PWM modifica la energía promedio suministrada bajo condiciones particulares, pero no asegura una relación lineal entre duty y velocidad; influyen carga, fricción y características del motor.

Registre duty, tensión de alimentación, respuesta observada, corriente y posible calentamiento. Para el cronómetro, documente errores acumulados a 30 s, 60 s y 120 s contra una referencia. El código, esquema de conexiones, pruebas de botones y evidencia OLED deben integrarse en el reporte del proyecto.

Ejemplo: acumulación y actualización del cronómetro

Si Timer_A emite un tick real cada 10 ms, cien ticks acumulan un segundo nominal. Para mostrar centésimas, el formato puede conservar un contador de ticks y derivar por separado segundos, minutos y centésimas. La pantalla OLED no necesita recibir una actualización completa cada 10 ms: puede refrescarse, por ejemplo, cada 100 ms sin alterar la cuenta de tiempo.

La orden Lap conserva una copia del tiempo acumulado, pero no debe reiniciar el contador que sigue ejecutándose. La orden Stop congela la acumulación; Reset restablece los registros del cronómetro conforme a su estado. Compruebe estos casos en el simulador antes de implementar el firmware y documente el error frente a un instrumento de referencia.

Base temporal del cronómetro con Timer_A

El código siguiente muestra una operación concreta del MSP430G2553. Identifique sus entradas, registros y condiciones iniciales antes de incorporarlo a la práctica.

#include <msp430.h>
#include <stdint.h>

volatile uint32_t ticks10ms = 0;
volatile uint8_t cronometro_activo = 0;

/* ISR: se ejecuta cada 10 ms, una vez configurado Timer0_A. */
#pragma vector=TIMER0_A0_VECTOR
__interrupt void timer0_a0_isr(void)
{
    if (cronometro_activo) {
        ++ticks10ms;
    }
}

/* Ejemplo: con SMCLK = 1 MHz, divisor 1 y modo UP,
   TA0CCR0 = 9999 produce un evento cada 10 ms.
   La pantalla OLED se actualiza a una frecuencia menor. */

Cada interrupción representa 10 ms únicamente si el reloj y TA0CCR0 fueron configurados como se indica. La variable compartida se declara volatile. Para leer de forma coherente un contador de 32 bits en una CPU de 16 bits, proteja el acceso frente a interrupciones concurrentes.
